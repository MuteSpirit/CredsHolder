# HLD. CredsHolder

## Introduction

This document contains common design for hardware credential manager. The main goal is defining requirements and available entities of system.

The concrete parts of device and use case scenarios will be designed separately.

## Abbreviations and Terms

* Hardware Credential Manager - separate device which store credentials
* HLD - High Level Design (see [CONTRIBUTING.md](/CONTRIBUTING.md) for details)
* Device - the same as CredsHolder, the common title of current project device - hardware credential manager
* OS - Operating System
* DIY - Do It Yourself
* FW - firmware
* RTOS - Real-Time OS
* OTP - One Time Password

## Use Cases

### Actors

* Developer - project participant
* User - common CredsHolder user independent on his job
* Corporate Employee - User on job in non-governmental company
* Governmental Employee - User on job in governmental company
* Intruder - person who would like to use CredsHolder without User approval
* Vendor - commercial company manufacturing CredsHolder devices

### User Stories

| No | User Story |
| --- | --- |
| S-1 | As a Developer I'd like to make work as best as possible and add link to project into my CV. |
| S-2 | As an User I'd like to use hardware credential manager CredsHolder to store personal accounts only. |
| S-3 | As an User I'd like to use CredsHolder with any of devices: desktop PC, laptop, smartphone, tablet. |
| S-4 | As an User I'd like that CredsHolder will fill login form/prompt itself. |
| S-5 | As an User I'd like to store about 1000 accounts on CredsHolder. |
| S-6 | As an User I'd like that CredsHolder has less vulnerabilities as possible. |
| S-7 | As a Developer I'd like to develop new features for CredsHolder but Users will not have to buy to model to start use them. |
| S-8 | As an User I'd like to save some money and assemble/repair CredsHolder myself as DIY device. |
| S-9 | As an User I'd like be able easy replace CredsHolder with full credentials migration to new CredsHolder if the current one is broken or User bought more modern CredsHolder model. |
| S-10 | As an User I'd like be sure that my credentials will be not compromised if CredsHolder is stolen by Intruder. |
| S-11 | As an User I'd like be able use CredsHolder by one human arm, left or right. |
| S-12 | As a Corporate Employee I'd like to use CredsHolder to store work accounts credentials. CredsHolder MUST all Corporate security standards. |

## Entities

Everyday CredsHolder use case should looks like next: 

1. User opens login form on own PC/laptop/smartphone
1. User plugs CredsHolder
2. User authenticates on CredsHolder
3. User chooses account on CredsHolder
4. CredsHolder fills login/password in login form on User's PC/laptop/smartphone

There are next entities according to scenario above:

| Name | Comment |
| --- | --- |
| User | Citizen, Corporate, Governmental |
| Interface between Device and PC/phone/laptop | e.g. USB cable, Bluetooth, Radio channel |
| Device Controller/SOC | e.g. Arduino, NRF52, etc. Limited CPU frequency, RAM and internal flash storage volume |
| Device UI | Device hardware/? parts which allow User to authenticate on device and navigate credentials, e.g. buttons, OLED, microphone, keyboard, vibration motor, sensor display, etc. |
| Device Persistent Storage | Some flash memory to store application data, e.g. EEPROM, NAND, etc. |
| Device Case | That case MUST contain all Device UI components |
| Device FW | Bootloader, Sketch/RTOS, ... working on Device |
| Device Authentication Procedure | Password, PIN, fingerprint, voice, other biometric, mind |
| Application Storage File System | SimpleFS, JFFS, FAT, extX, UBIFS, BTRFS, XFS, etc. |
| Application Storage | (Encrypted) block device |
| Application DB | e.g. raw file, SQL, NoSQL, JSON, BSON, etc. |
| Application Data | Credentials, OTP, etc. |
| Application Settings | |
| Encryption Algorithm | e.g. AES-256 or local government algorithm |
| Hash Function | e.g. Whirlpool or SHA-512 or local government algorithm |

### Application Data. Account Credentials

Object which contains information needed to pass authentication on some service/device for User account.

Minimally it contains login and password.

But if see wider then it may contain additional fields:
* Account Name - it may be a name of web site or application, PC/server hostname or some device/application nickname
* URL of resource
* email
* phone number
* previous password
* used password generation policy
* expiration date/time

## Notes

* KEK - Key Encryption Key - key used to encrypt MEK
* MEK - Media Encryption Key - key to encrypt application data

| Encryption algorithm | e.g. AES-256 because it's well known algorithms without known backdoor and used by militaries. |
| Hash function (KDF) | e.g. Whirlpool or SHA-512. Whirlpool is less common and slower. That will increase time for KEK bruteforce. |
